# 0b track C results (2026-09-24 PDT)

Engine lifecycle for plugin reload, Location reload, and companion removal. Live suite: `plugins/provider-opencode/src/bridge/companion-reload.live.test.ts`. Companion: `src/server.ts` on `spike-0b-track-c`.

Passed on both Shuvcode 2.0.15-shuv.1 and stock `@opencode/cli@2.0.15` (Bun-compiled Linux x64), except the Location inactivity TTL case, which released binaries cannot exercise. Unit check `pnpm exec turbo run typecheck test --filter=bb-plugin-provider-opencode`: 241 passed, live suites skipped.

Activation order observed in `GET /api/plugin` (after builtins): discovered directory plugin `bb-spike-early` (`config/<appId>/plugin/aaa-early`), then configured companion `bb.tools`, then configured `bb-spike-later`. That matches plan N11 (directory plugins sorted by path, then configured packages in config order). Marker plugins expose `bb.spike.early` / `bb.spike.later` `hello` generations so a restart is visible without relying on `plugin.updated` alone.

There is no plugin-reload HTTP route. `packages/protocol/src/groups/plugin.ts` only has `plugin.list`, `plugin.check`, and `plugin.update`.

- **Generation.** Companion `hello` returns `{ protocol: "bb.tools.v1", version: 1, generation, features }`. `generation` is a random token created once per plugin activation, stable across two `hello` calls, and different after reload. The bridge records it with the attach `bindingID` (epoch) and capability. Before every `turn/start` and `turn/steer` it calls `hello` plus `status` (`{ capability }` → `{ bound, generation, epoch }`) and reattaches from retained descriptors on mismatch or unbound. A held binding does not warn `reattached bb tools` and a second turn still advertises `bb_echo`. Both engines.
- **Companion hot reload during a claimed call.** Trigger: rewrite the companion entrypoint `server.ts` (content change; configured-directory watch plus module source watch). Pickup 153ms (Shuvcode) and 145ms (stock) until `hello` generation changed. `plugin.updated` fired. The earlier marker generation stayed the same; the later marker generation changed, so plugins after the companion restarted and the unchanged prefix did not. In-flight call: `session.tool.failed` with `error.type: "tool.execution"`, `error.message: "bb tool outcome is uncertain: the companion generation ended before the result was delivered"`, `executed: false`. No `session.tool.success`. The bridge emitted one `item/tool/call`. Answering that reverse call after the failure warned `could not deliver bb tool result …; not retrying into a new companion generation` and did not send a second reverse call. The same turn did not continue: `session.execution.failed` with `error.type: "provider.no-route"` and `error.message: "No model is available for session <id>"` (both engines). The next `turn/start` warned `reattached bb tools for <thread>: generation <old> -> <new>` before the prompt, the model request included `bb_echo`, and a new call round-tripped (`echo: again`). Other events in the burst: `provider.updated`, `model.updated`, `skill.updated`, `command.updated`, `agent.updated`, `integration.updated`, `websearch.updated`, `reference.updated`.
- **Earlier-ordered plugin change during a claimed call.** Trigger: rewrite `config/<appId>/plugin/aaa-early/server.ts` (discovered directory plugin, before the companion). Pickup 155ms (Shuvcode) and 143ms (stock). Companion generation changed, and both the early and later marker generations changed, so the companion and everything after it restarted. Same uncertain `session.tool.failed` (`executed: false`), one reverse call, late delivery warned and was not retried, `session.execution.failed` was emitted, and the next `turn/start` reattached and round-tripped. Both engines.
- **Later-ordered plugin change.** Trigger: rewrite the configured plugin listed after the companion. Pickup 121ms (Shuvcode) and 120ms (stock). Companion generation and the earlier marker generation were unchanged; only the later marker changed. The claimed call was answered successfully (`echo: hold` in the next model request). No `session.tool.failed`, no reattach warning, no late-delivery warning. `plugin.updated` still fired. Binding stayed intact on both engines.
- **Location reload between turns.** Trigger: `POST /api/location/reload` (no body; 204). Pickup 92ms (Shuvcode) and 72ms (stock) until `hello` generation changed. `location.shutdown` fired, then the replacement graph's `plugin.updated`. All three plugin generations changed (the Location service graph was replaced, not a prefix restart). The idle session stayed usable: the prior turn had `session.execution.succeeded`. The next `turn/start` reattached from retained descriptors and a `bb_echo` call round-tripped. Both engines. This is also the proxy for an idle session after Location eviction.
- **Location eviction (inactivity TTL).** Not live-proven, and not waited out. `LocationActivity.node` is `layer()` with no arguments (`packages/core/src/location-activity.ts`). Defaults are `timeToLive: "60 minutes"` and `sweepInterval: "1 minute"`. The sweep interrupts active executions with `reason: "inactivity"` and then invalidates the Location. Neither released binary contains `LOCATION_TTL`, `LOCATION_ACTIVITY`, or `OPENCODE_LOCATION`. Both contain `60 minutes` and `inactivity`. No config field or CLI flag supplies the TTL. An in-flight bb call across the TTL therefore cannot be shown on these binaries; source says stock engines interrupt it as inactivity and then drop the graph, which is the same undeliverable-result class as plugin disposal (uncertain, not success). Idle-then-next-turn is covered by Location reload above.
- **Companion removal during a claimed call.** Trigger: delete the companion path from the engine config `plugins` array (`config/<appId>/opencode.json`). Pickup 254ms (Shuvcode) and 243ms (stock) until `hello` failed. `config.updated` then `plugin.updated`. The earlier marker generation stayed the same; the later marker generation changed (removing the companion restarts plugins that sort after it). The claimed call settled `session.tool.failed` with the same uncertain `tool.execution` message, `executed: false`, and was not re-dispatched. Late delivery warned and was not retried. `session.execution.failed` was emitted. The next `turn/start` succeeded native-only: the model request did not include `bb_echo`, no further `item/tool/call` was sent, and the bridge emitted `provider.warning` via `warnDroppedTools` (`Dropped dynamicTools: bb_echo`, summary `OpenCode does not run bb plugin tools`). It did not fail the turn. Both engines.
- **Incompatible companion.** `BB_TOOLS_PROTOCOL_VERSION=99` makes `hello` report version 99. `thread/start` succeeds and does not emit the dropped-tools warning. `turn/start` fails before prompting with `OpenCode companion bb.tools.v1 protocol version 99 is not supported (supported version: 1). Install a compatible opencode-bb-tools release with the engine's \`plugin add opencode-bb-tools\` and retry the turn.` No tool-bearing model request. Both engines. `turn/steer` uses the same `ensureBbTools` check before the steer-specific stale-turn branch.

## Findings / deviations from plan

- **`session.context` cannot fail the step.** Plan binding step 9 says a generation change during a turn should make `session.context` fail the step with `bb tools reattaching` instead of exposing an empty catalog, then the bridge reattaches and the turn continues. Session hooks have a `never` failure channel (`packages/core/src/plugin/hooks.ts`, `NoFailures<SessionHooks>`). A throw disables the plugin group (plan binding step 5). That step-failure was not implemented. No bb core change was made.
- **The in-flight turn does not continue.** After companion disposal the tool settles uncertain, then the execution fails with `provider.no-route` / `No model is available for session …` before another model request. Reattach happens on the next `turn/start` or `turn/steer`, not mid-turn, and that next turn round-trips. A late result is warned and not retried into the new generation.
- **TTL is not injectable on released binaries.** Milestone 1b's in-flight lease is still required before a call can outlive 60 minutes. This track did not patch the engine.
- **Binding check is generation + epoch + `status.bound`.** Catalog digest is not compared. `status` is the cheap check the plan's "e.g. status" allowed. Hello generation is the Location/plugin generation id.

## Spike shortcuts left

- No owner heartbeat, attach-takeover fencing, or catalog-digest compare. `status` returns epoch but the bridge only uses it to detect a replaced binding.
- Supported protocol is exactly version 1, not a range. The version override is the test env var `BB_TOOLS_PROTOCOL_VERSION`.
- No duplicate `bb.tools.v1` detection.
- Mid-turn `bb tools reattaching` step failure is not implemented (infeasible on the current hook channel).
- Disposal settlement is a companion scope finalizer (`bb tool outcome is uncertain: the companion generation ended before the result was delivered`), not an engine interrupt of the session fiber. The engine then fails the execution itself with `provider.no-route`.
